# webkernel/codebase

Application bootstrap and runtime integration package. Composer maps `Webkernel\Codebase\` to `src/`; the public `Webkernel\Http` entry point uses an explicit class map. Package declarations and the Codebase service provider live under `Webkernel\Codebase\Providers` in `src/Providers/`.

The host project owns configuration in `webkernel/config/`; `webkernel/config` provides the configuration package and does not duplicate those application settings. The host Composer path repository discovers framework packages under `webkernel-src/` and symlinks them into `internal/dependencies` when installed.

During Composer install, update, and autoload generation, Codebase reads each package's `extra.webkernel.provider` and verifies that it extends the shared `ServiceProvider`, and compiles bindings, route, view, component, language path, command, panel, asset entry-point, public asset root, and package metadata manifests. A package sets `extra.webkernel.package-declaration` to an autoloadable class extending `Webkernel\Packages\PackagesMetadatas`; that class returns its namespace prefix and localized catalog metadata as native PHP arrays. Composer compiles these declarations into `webkernel_packages.php`, which requests read directly without scanning package manifests or refreshing JSON metadata. `ServiceProvider::ASSETS` records frontend build source files; `ServiceProvider::PUBLIC_ASSETS` declares directories whose files may be served. `GetAsset::url('vendor/package', 'resources/assets/logo.svg')` produces `/__webkernel-app/assets/vendor/package/resources/assets/logo.svg`. The route resolves the package from the compiled declaration, validates the canonical path beneath a declared root, and serves only approved MIME types. Package roots are atomically compiled by Change Watcher. `PackageAssetRegistry` observes the generated roots manifest with Change Watcher once per request when assets are used, so persistent workers reload it after Composer installs or updates a module without scanning package directories. `./platform deploy` copies supported declared assets under the matching URL tree in `public/`, using per-file atomic replacement; the package route remains the fallback if a deployed copy is absent. Hashed build filenames receive immutable caching; un-hashed files revalidate. Localized text is returned as locale maps so the consumer can select the active locale and apply its normal fallback. Branding images retain their dedicated catalog asset route. Requests do not scan package directories or discover providers.

`GetAsset::url()` appends a short SHA-256 content version to every declared file URL. A changed asset therefore gets a new browser URL even when the package release version is unchanged; templates should not maintain manual cache-busting values.

Composer compiles package Vite manifests into `webkernel_vite.php`. Requests load that manifest only when a rendered view asks for a Vite asset; `GetAsset::vite()` resolves script entries and `GetAsset::viteStyles()` resolves CSS-only entries. There is no request-time package or asset scan.

`Webkernel\\Http::run()` boots Config and the PSR-11 Container, clears request-scoped services, configures the view and language catalogs, then dispatches through `Webkernel\\Route\\Route`. Route files load from the compiled route manifest inside the router. The application root comes from Composer's installed root-package metadata rather than the process working directory.

Codebase requires Lifecycle, Config, Container, Database and Models, Change Watcher, I18n, Route, ServiceProvider, View, Console, and the built-in Commands package. The front controller and console door remain separate entry points.

Codebase also requires the `webkernel/system-panel` and `webkernel/system-installer` framework packages. They currently supply package metadata and empty service providers; their administration and installation interfaces remain planned. Composer installs these libraries under the application's `internal/dependencies/webkernel/` directory.

The compiler also reads the application's `config/providers.php` when present. This file returns a list of classes extending `Webkernel\ServiceProvider`, such as `App\Providers\AppServiceProvider`. It supplements package providers; duplicate classes are processed once before compiling bindings and other declarations. Configured providers retain their installed package's prefix and asset root when their source belongs to that package, otherwise they use the application context. Invalid lists or provider classes fail compilation before publishing manifests. Changes require `./composer dump-autoload`; requests consume the generated manifests.
